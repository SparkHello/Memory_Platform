# Web Console 视觉观感、文案精简与易用性 — 实施计划

## Summary

让 Memory Console 对非技术用户默认直观、藏起技术细节，同时收敛视觉与文案。三条主线：视觉收敛（对比度/危险等级一致性/移动端死样式）、文案减负（术语清理/命名统一）、易用性（简洁模式补全核心功能 + 内容降级呈现）。机制上**复用已有**的 token 体系（`tokens.css`）、深/浅双主题、简洁/专家双模式（`AppShell.tsx` 的 `SIMPLE_NAV_SECTIONS`/`NAV_SECTIONS`、`App.tsx` 的 `uiMode`），不新建框架。

**范围边界**（遵循需求草稿）：不做组件拆分、路由重构等工程改动；不处理已修复项（复制 token 静默失败、401 全局处理）。

## 关键事实核查（计划依据，修正需求草稿两处）

- ✅ **简洁/专家双模式已存在**：`App.tsx:62` `uiMode` 状态（`loadUiMode()` 持久化）、`AppShell.tsx:118/390` 按模式切 `SIMPLE_NAV_SECTIONS`/`NAV_SECTIONS`。
- ✅ **简洁模式当前导航**（`navigation.ts:54-58`）：开始=工作室，内容=记忆库+知识库，使用=模型与路由+报告与备份+接入信息。**知识库已在**。
- ⚠️ **体检(review)、用量(usage) 只在专家模式**（`NAV_SECTIONS` 治理组/数据组，`navigation.ts:41-48`）。
- ⚠️ **`UsagePage`/`ReviewPage` 均不接收 `expertMode` prop**（`UsagePage.tsx` 子组件签名 `{summary, setupStatus}`；`ReviewPage.tsx:53-62` props 仅 `api/notify/confirm/openMemory/setupStatus`）——降级呈现需新增入参。
- ⚠️ **技术字段裸露确证**：`UsagePage.tsx`「实际 Deployment」标题(L152)、「Deployment」表头(L161)、`<code>{deployment_id}</code>`(L171)、「逐 Attempt 账本」(L131)、「Token」表头(L163)；`EvaluationPage.tsx:483` 裸露 `record_usage`/`embedding`；`MemoryDetailDrawer.tsx:460` 显示 `embedding_space_id`。
- 🔧 **修正**：`connect_client` 引导**已存在**（`DashboardPage.tsx:483-485` 条件渲染 `ConnectClientCard`，L1165/L1213），草稿"前端没消费"不准确。真实问题是**可见性/优先级**：卡片是否进入简洁模式工作室首屏、是否被其他 action card 淹没。
- ✅ **编辑记忆确认弹窗确证**：`MemoryDetailDrawer.tsx:254` `saveEdit` 内无条件 `confirm({title:"更新记忆", tone:"warning"})`，每次保存必弹；删除在 L303 `tone:"danger"`。
- ✅ **action card 迷路页确证**：`DashboardPage.tsx` `buildStudioActions`(L1269-1349) 7 张卡中，`review`/`evaluation`/`core` 三张目标页**不在**简洁导航。

## Steps

按 value-per-effort 排序，高价值低成本优先。

### 阶段 0 — 基线验证（先确认"疑似"，避免误改）

- [ ] 写一个对比度验证脚本（Node 脚本读 `tokens.css` 的 `:root` 与 `[data-theme="light"]` token，计算正文/muted 文字对各自背景的 WCAG 对比度），跑深/浅两主题，输出不达标的 token 对清单。浅色主题注释声称"≥6.5:1 经脚本验证"但脚本未入库，需重建并覆盖深色。
- [ ] 用脚本/全文搜索产出"用户可见术语裸露清单"定稿（基于上述核查 + 补全 grep 截断遗漏），逐项标注"简洁模式隐藏 / 全模式改写 / 保留"。

### 阶段 1 — 易用性（核心价值，面向非技术用户）

- [ ] **体检/用量进简洁导航**：`navigation.ts` `SIMPLE_NAV_SECTIONS` 增补 `review`（体检）、`usage`（用量）。知识库已在，无需动。
- [ ] **体检/用量页降级呈现**：给 `UsagePage`、`ReviewPage` 新增 `expertMode` prop（从 `App.tsx` 的 `uiMode === "expert"` 透传，与 `App.tsx:436/478` 现有用法一致）。简洁模式下：
  - `UsagePage`：隐藏「实际 Deployment」面板、`deployment_id` code 列、「逐 Attempt 账本」技术列，保留「已知实际费用」「调用完整度」「输入/输出 Token」等结果性指标；技术字段收进"详情"折叠或仅专家模式可见。
  - `ReviewPage`：保留 severity 分组建议、健康检查结果等结论；`revisionPreview`/`next_action_options`/决策日志来源等技术细节降级（默认折叠或专家模式）。
  - **形态选择**：字段级隐藏优先（改动最小、可控）；结构性技术面板用"默认折叠 + 专家模式展开"。
- [ ] **action card 迷路修复**：`DashboardPage.tsx` `buildStudioActions` 中 `review`/`evaluation`/`core` 三张卡，在简洁模式下或不显示、或跳转目标改为简洁导航内页面（如 `review` 卡现在能进导航了，`evaluation`/`core` 卡简洁模式下隐藏或降级为提示）。保证简洁模式里"所见即可达"。
- [ ] **首次引导可见性**：确认 `ConnectClientCard`（`DashboardPage.tsx:483-485`）在简洁模式工作室首屏的优先级与可见性，必要时提升排序/视觉权重，确保"模型已就绪但未接客户端"的用户一眼看到下一步。

### 阶段 2 — 文案减负

- [ ] **术语清理**：按阶段 0 清单执行。用户可见的 `deployment`/`revision`/`CAS`/`X-User-Id`/`embedding`/`record_usage`/`outbox` 等，在简洁模式隐藏、在专家模式改写为业务语言（如 "Deployment"→"渠道与模型"、技术 ID 进详情/`<code>` 折叠）。
- [ ] **命名统一**：「接入信息/客户端接入/接入/设备接入」统一为一个词（建议「客户端接入」），全局替换 `navigation.ts:24` label/shortLabel、`DashboardPage.tsx:1217/1263/1290` 等使用点。
- [ ] **误导性文案**：核查搜索"20 条上限×客户端筛选"计数，改为如实表述（如"前 20 条结果"或提示可 refine）。
- [ ] **确认弹窗减负**：移除 `MemoryDetailDrawer.tsx:254` 编辑保存的 warning 确认（低风险、可撤销的操作直接生效）；保留 L303 删除的 danger 确认。统一 warning/danger 的语义：danger=不可逆/破坏性，warning=需谨慎，编辑类不弹。

### 阶段 3 — 视觉收敛

- [ ] **对比度修复**：按阶段 0 脚本输出的不达标清单，调整深色主题 `rgba(255,255,255,0.x)` 文字 token，直至深/浅两主题正文/muted 对比度均 ≥ 4.5:1。验证脚本入库（如 `ui/scripts/check-contrast.mjs`）并在 CI/测试中可复跑。
- [ ] **危险等级一致性**：统一 warning/danger 的视觉样式与确认弹窗触发规则（与阶段 2 确认弹窗减负对齐），确保同类风险同等呈现。
- [ ] **移动端死样式清理**：删除/修复 `pages.css` 780px 断点下被 `morning-crystal.css` 覆盖的约 35 行 sidebar 死代码；确认首配阶段底栏「模型」入口在简洁模式可见。
- [ ] **token 收口**：移除 `MemoriesPage.tsx:497,535` 硬编码色值，改用 token；全库扫描确保 TSX 内联样式不引入 token 外色值。

### 阶段 4 — 文档与回归

- [ ] 视改动规模决定是否补一份轻量 `DESIGN.md` 或在 `ui/README` 记录设计 token 与双主题约定（YAGNI：若 token 注释已足够则不新建文件）。
- [ ] 全量回归（见 Tests）。

## Acceptance Criteria（映射需求验收标准）

1. 对比度：深/浅主题正文与 muted ≥ 4.5:1，脚本留记录（`ui/scripts/check-contrast.mjs`）。
2. 术语：用户可见字符串不含 deployment/revision/CAS/X-User-Id 等内部标识符；「客户端接入」命名全 UI 唯一。
3. 确认弹窗：仅 danger 级弹确认；编辑记忆直接保存；warning/danger 视觉一致。
4. 简洁模式：导航含知识库/体检/用量；体检/用量简洁模式只呈现结果与结论；action card 无迷路页；`connect_client` 有首屏引导；核心任务不出简洁模式。
5. 移动端：780px 下无 sidebar 死样式；TSX 内联样式无 token 外色值。
6. 回归：`scripts/test.sh` + `npm run build` 通过，e2e 不回归。

## Risks — Pre-mortem

**Tigers（真实风险，需处理）**

- **T1（Fast-Follow）**：降级呈现"藏过头"——把非技术用户也关心的有用信息（如某条记忆为何被体检标记的原因）一并隐藏，反而更难用。*缓解*：降级只藏"技术实现字段"（deployment\_id、revision、CAS、embedding），保留"结论与原因"（为什么标记、建议怎么做）；折叠而非删除，需要时可展开。
- **T2（Launch-Blocking）**：对比度调整破坏深色主题"暮色琥珀"的设计调性——为达标把玻璃质感的半透明文字全改成纯白，视觉上变成普通深色后台。*缓解*：只调到 4.5:1 阈值即止，优先提升文字透明度而非改背景；由设计 token 统一调，不逐组件硬改。*负责人*：实施者。*决策点*：阶段 3 对比度修复完成后视觉走查。
- **T3（Fast-Follow）**：术语"业务化改写"过度，专家用户找不到原有技术概念（如把 Deployment 改得太隐晦，排障时反而看不懂）。*缓解*：专家模式保留技术术语原文，简洁模式才用业务语言；两模式文案映射集中管理，不散落各组件。

**Paper Tigers（他人可能担心，本计划判断非问题，记录以对齐）**

- "改动页面多、工作量大"：实际核心是导航数组 + 两个页面加 `expertMode` 分支 + 文案替换 + token 调整，无新增依赖、无架构改动，可控。
- "需要新建设计系统/DESIGN.md"：token 体系已存在且注释完整，按 YAGNI 不强制新建文件。

**Elephants（未明说、需在实施中留意）**

- 需求草稿两处与现状不符（`connect_client` 已存在、知识库已在简洁模式），提示**可能还有其它"疑似"项与实际代码有出入**。阶段 0 的基线验证就是为此而设——先确认再动手，避免照着过时的背景误改。
- "简洁模式到底藏多少"没有客观标准，最终边界（哪些字段算"技术细节"）需在实施中逐个页面与用户/设计确认，本计划给的是判定原则而非穷举清单。

## Sequencing &amp; Prioritization（依据）

- **阶段 1（易用性）排第一**：Opportunity Score 最高——对非技术用户 Importance 高、当前 Satisfaction 低（核心功能缺失/迷路）；且 ICE 中 Ease 不低（导航是数组改动、expertMode 是已有模式）。
- **阶段 0 前置**：低成本（一个脚本 + 一次清点）但能消除草稿里两处事实错误带来的误改风险，是后续所有阶段的前提。
- **阶段 2、3 随后**：文案与视觉是 Importance 高但 Satisfaction 中等的问题，依赖阶段 0 的清单。
- **明确延后（Won't for this release）**：组件拆分（`ProvidersPage.tsx` 1323 行等）、路由库引入、新建完整 DESIGN.md——超出本需求"视觉/文案/易用性"范围，属工程债，另立项。
